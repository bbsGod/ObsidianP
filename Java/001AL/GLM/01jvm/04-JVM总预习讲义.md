# 第一单元 · JVM 内存结构

## 1.1 运行时数据区总览

JVM 运行时内存分**线程私有**和**线程共享**两类：

| 区域 | 归属 | 存什么 | 关键点 |
|------|------|--------|--------|
| 程序计数器 | 线程私有 | 当前线程执行的字节码**行号指示器** | 线程切换后靠它恢复执行位置；native 方法时为 undefined；**不会 OOM** |
| 虚拟机栈 | 线程私有 | 栈帧（局部变量表、操作数栈、动态链接、方法出口） | 深度超限抛 StackOverflowError |
| 本地方法栈 | 线程私有 | 为 native 方法服务（C/C++ 实现） | 与虚拟机栈类似，对象是本地方法 |
| 堆 | 线程共享 | 对象实例、数组 | GC 主战场 |
| 方法区 | 线程共享 | 类元信息、运行时常量池 | JDK8 起由**元空间**实现，在**本地内存** |

> ⚠ 高频坑：线程私有区是**三个**（计数器、虚拟机栈、本地方法栈），少答一个就丢分。

## 1.2 堆的内部划分

```
堆 = 新生代（Young） + 老年代（Old）
新生代 = Eden + Survivor0(From) + Survivor1(To)   // 默认 8:1:1
```

- 新对象优先 Eden；Eden 满 → Minor GC，存活对象复制到 Survivor，年龄 +1
- 年龄到阈值（默认 15，`-XX:MaxTenuringThreshold`）→ 晋升老年代
- **TLAB**：每个线程在 Eden 划一块私有分配区，分配对象只动指针（指针碰撞），消除多线程争抢

## 1.3 方法区演进（JDK 7 → 8）⭐必考

| | JDK7 及以前 | JDK8+ |
|--|------------|-------|
| 实现 | 永久代 PermGen（JVM 内存内） | 元空间 Metaspace（**本地内存**） |
| 大小 | -XX:PermSize 固定 | -XX:MaxMetaspaceSize，受本机内存限制 |
| 溢出 | 易 PermGen OOM | 不易（但类加载泄漏仍会吃光内存） |

**JDK8 的拆分（画布反复记的重点，结论是）：**
- static 静态变量 → 移到**堆**中的 Class 对象里
- 字符串常量池 → 移到**堆**

> 一句话记牢：**JDK7 起 static 变量迁出永久代；JDK8 静态变量、字符串常量池都在堆里。** 规范说"静态变量归方法区"是逻辑概念，HotSpot 实现放堆。

## 1.4 直接内存 & 栈溢出

- 直接内存：`ByteBuffer.allocateDirect()`，用本地内存，NIO 零拷贝；不属 JVM 运行时数据区但受 OOM 影响
- 栈溢出（SOFE）：无出口递归；`-Xss` 调栈大小（默认 1M）
- 对比：SOFE 是栈深超限，OOM 是空间不足——一个在栈、一个在堆/元空间

# 第二单元 · 类加载机制

## 2.1 类生命周期（五阶段）

```
加载 → 验证 → 准备 → 解析 → 初始化
```

| 阶段 | 做什么 | 易错点 |
|------|--------|--------|
| 加载 | 全限定名取二进制字节流 → 内存生成 Class 对象 | 由类加载器完成 |
| 验证 | 四道检查（文件格式/元数据/字节码/符号引用） | 保证符合 JVM 规范 |
| 准备 | 静态变量**分配内存、赋默认零值** | int=0、引用=null（不是代码里的值） |
| 解析 | 符号引用 → 直接引用 | 可发生在初始化之后（动态绑定） |
| 初始化 | 执行 `<clinit>`：静态变量真实赋值 + 静态代码块 | 触发时机=主动引用 |

**准备 vs 初始化**（必考）：准备给零值，初始化给代码写的真实值。

**符号引用 → 直接引用**（画布通俗版）：编译期不知道类加载到哪块内存，class 文件存字符串 `User.sayHello:()V`（符号引用）；运行到这行时找到内存真实地址替换（直接引用），之后直接跳地址执行。

## 2.2 类初始化顺序（代码题高频）

> 第一次 new 子类：**父静态 → 子静态 → 父实例代码块 → 父构造 → 子实例代码块 → 子构造**
> 静态块只执行一次（类只初始化一次）；实例块每次 new 都执行，且先于构造方法。

## 2.3 主动引用 vs 被动引用

**主动引用（触发初始化）**：① new；② 读写静态字段（非 final 常量）；③ 反射 Class.forName；④ 子类初始化先触发父类；⑤ main 所在类。

**被动引用（不触发）**：读 static final 常量（编译期入常量池）、数组定义 `A[] arr`、子类引用父类静态字段（只初始化父类）。

## 2.4 类加载器 & 双亲委派

**四类加载器**：Bootstrap（核心库 rt.jar）→ Extension（ext 目录）→ Application（classpath）→ 自定义。

**双亲委派**：子加载器先层层向上委托，父能加载就加载，不能才下放回子。
- 两大好处：①避免重复加载；②**安全**——java.lang.String 永远由 Bootstrap 加载，防篡改
- 生活类比：孙子有事找爸爸，爸爸找爷爷，爷爷干不了才自己干

**打破双亲委派**：SPI/JDBC（线程上下文类加载器反向委托）、Tomcat（webapp 隔离，先自己加载）、热部署/OSGi。
**自定义类加载器**：继承 ClassLoader，重写 `findClass()`（不是 loadClass）。

# 第三单元 · 垃圾回收

## 3.1 对象存活的判断

**引用计数法**：给对象配计数器，归零回收；**缺陷：无法解决循环引用**（A↔B 互相引用），主流 JVM 不用。

**可达性分析**：从 GC Roots 递归扫描，引用链达不到的即垃圾。
**GC Roots 四种**：虚拟机栈局部变量、本地方法栈 JNI 引用、类静态变量、运行时常量池常量。

**四种引用**（高频）：

| 引用 | 类 | 回收时机 | 应用 |
|------|-----|----------|------|
| 强 | 普通 new | 宁 OOM 不回收 | 普通对象 |
| 软 | SoftReference | **内存不足时** | 缓存 |
| 弱 | WeakReference | 下次 GC 必回收 | ThreadLocalMap 的 key |
| 虚 | PhantomReference | 随时，get 恒 null | 堆外内存回收通知（配引用队列） |

**finalize 自救**：不可达对象若重写 finalize() 且未执行过，有一次自救机会；已废弃（JDK9）。

## 3.2 三种回收算法

| 算法 | 优点 | 缺点 | 应用 |
|------|------|------|------|
| 标记-清除 | 简单、不动对象 | **碎片** | 老年代（CMS） |
| 复制 | 无碎片、快 | 空间减半 | **新生代**（存活率低） |
| 标记-整理 | 无碎片 | 需移动对象、慢 | 老年代 |

> 新生代用复制算法：对象 98% 朝生夕死，只搬活的，成本极低；8:1:1 空间浪费仅 10%。

## 3.3 GC 类型与触发

| 类型 | 范围 | 触发 |
|------|------|------|
| Minor GC | 新生代 | Eden 满（快、频繁、正常） |
| Major GC | 老年代 | 老年代不足 |
| Full GC | 整堆+方法区 | 老年代不足/元空间不足/System.gc()/分配担保失败/CMS 并发失败 |

**空间分配担保**：Minor 前若老年代放不下新生代全部对象，按历次晋升均值担保，没把握就直接先 Full GC。

## 3.4 三大收集器

| | ParallelGC | CMS | G1 |
|--|-----------|-----|----|
| 算法 | 复制+整理 | 标记-清除 | Region 化跨 Region 复制 |
| 停顿 | 全程 STW、长 | 低停顿 | **可预测停顿** |
| 碎片 | 少 | 多 | 无 |
| 定位 | 高吞吐 | 低延迟（已废弃） | 低延迟、服务端默认 |

**JDK 默认 GC 演进**：JDK6/7/8 → ParallelGC（你命令行验证过 `-XX:+UseParallelGC`）；JDK9+ 服务端（≥2核+≥1792M）→ G1，否则 Serial；JDK14+ 移除 CMS。

**并行 vs 并发**（易混，你专门记过）：
- 并行 = STW 暂停所有应用线程，多 GC 线程同时干活
- 并发 = GC 线程和应用线程一起跑，不 STW
- ParallelGC 全程并行无并发；CMS 并发标记+清除；G1 并发标记 + STW 并行拷贝 = 混合型

## 3.5 CMS 详解

**四阶段**：①初始标记（STW，标 GC Roots 直连）→ ②并发标记 → ③重新标记（STW，修正并发期变动）→ ④并发清除。

**四缺点**：①碎片；②并发失败退化为 Serial Old 长停顿；③**浮动垃圾**（并发清除期间新产生的垃圾本轮收不到，需预留空间）；④并发阶段抢 CPU。

## 3.6 G1 详解

- 堆拆成独立小 Region（逻辑分代、物理不分代）
- 可预测停顿：每次 GC 前估算各 Region 回收耗时收益，**动态挑选**回收哪些 Region，控总量
- `-XX:MaxGCPauseMillis`（默认 200ms，期望值非硬保证）
- Mixed GC：一轮同时回收年轻 Region + 部分高收益老年代 Region
- **缺点（标准答案）：吞吐量低于 ParallelGC**（为低延迟做的权衡），Region 维护有额外内存开销

## 3.7 ZGC（加分）

JDK11 引入、15 生产可用；停顿 <1ms 不随堆大小增长；染色指针 + 读屏障。堆 ≤8G 用 G1，超大堆/极致低延迟用 ZGC。

# 第四单元 · JVM 调优（你的实战强项）

## 4.1 方法论骨架

```
定目标（吞吐 or 延迟→选收集器）→ 监控 → 定位（决策树）→ 动手 → 验证
```

## 4.2 监控工具链

| 工具 | 作用 | 命令 |
|------|------|------|
| jps | 找进程 | `jps -l` |
| jstat | GC 统计（第一工具） | `jstat -gcutil <pid> 1000` |
| jmap | 堆快照 | `jmap -dump:format=b,file=heap.hprof <pid>` |
| jstack | 线程快照 | `jstack <pid>` |
| jcmd | 综合诊断 | `jcmd <pid> GC.heap_info` |
| Arthas | 线上诊断 | `dashboard` / `thread -n 3` / `heapdump` |

**jstat -gcutil 列**：S0 S1 E O M YGC YGCT FGC FGCT GCT（**O=老年代使用率**，排查 Full GC 看它和 FGC）。

## 4.3 GC 日志解读

- 打印（JDK8）：`-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log`
- 打印（JDK9+）：`-Xlog:gc*:file=gc.log:...`（⚠ JDK8 不支持 -Xlog 语法）
- 看一条 Full GC：`Tenured: 6142M->2048M->8192M` = 老年代回收前→后→容量；**回收后仍接近容量=泄漏或堆太小**
- 诊断口径：FGC 持续涨 + O 列不落 → 老年代问题；YGC 频繁但 FGC 少 → Eden 偏小

## 4.4 问题定位决策树

```
频繁 Minor GC → Eden 太小 → 调 -Xmn
频繁 Full GC：
  回收后 O 明显降 → 堆太小/晋升过快 → -Xmx、MaxTenuringThreshold
  回收后 O 不降 → 内存泄漏 → jmap 导堆 → MAT 看 Dominator/Leak Suspects
    → 定位（未关闭资源、长生命周期大对象、无上限缓存）→ 改代码
单次停顿长 → STW 不可控 → 换 G1 + MaxGCPauseMillis
Metaspace 顶满 → 动态类生成（CGLIB）→ 加大上限 / 查类泄漏
```

## 4.5 OOM 类型大全

| OOM | 原因 | 处理 |
|-----|------|------|
| Java heap space | 堆放不下 | -Xmx / MAT 查泄漏 |
| Metaspace | 类元数据超限 | MaxMetaspaceSize / 查类泄漏 |
| GC overhead limit exceeded | 98% 时间 GC 却回收不到 2% | 等价堆耗尽 |
| unable to create new native thread | 线程到系统上限 | **减小** -Xss、降线程、ulimit |
| Direct buffer memory | 直接内存耗尽 | MaxDirectMemorySize |

**泄漏 vs 溢出**：泄漏是原因（该死不死），溢出是结果（装不下）。

## 4.6 容器化 JVM（你的实战区）

- `-XX:+UseContainerSupport`：JDK8u191+ 感知容器 limit（否则按宿主机算默认堆，易被 OOMKilled）
- `-XX:MaxRAMPercentage=75.0`：按容器 limit 比例给堆
- **HeapDumpPath 坑**：容器重启 dump 丢失，必须挂载卷
- `-Djava.security.egd=file:/dev/./urandom`：修容器熵不足启动慢
- `-Dfile.encoding=UTF-8`：信创麒麟乱码

## 4.7 生产参数模板（你的 Docker 12 条精华）

```bash
-Xms1024m -Xmx4096m                 # 容器 limit 要 5~6G，给元空间/栈/native 留量
-XX:MetaspaceSize=128m              # 初始即高水位，避免启动频繁 Full GC
-XX:MaxMetaspaceSize=512m           # 防类加载泄漏吃光内存
-XX:+UseG1GC -XX:MaxGCPauseMillis=200
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dump.hprof
```

# 附 · 一分钟速记卡

- 线程私有 3 个：计数器、虚拟机栈、本地方法栈
- JDK8 三件套：元空间（本地内存）、静态变量→堆、字符串常量池→堆
- 类加载五阶段：加载→验证→准备→解析→初始化（准备给零值，初始化给真值）
- 双亲委派两大好处：防重复、保安全；打破靠 findClass / 线程上下文
- GC 判断：引用计数（循环引用死穴）→ 可达性分析（GC Roots 四种）
- 四种引用：强软弱虚，软=内存不足才收，弱=GC 就收
- 新生代复制、老年代整理、CMS 清除（碎片）
- CMS 四阶段：初始标记→并发标记→重新标记→并发清除
- G1 = Region + 可预测停顿 + Mixed GC；缺点=吞吐低于 Parallel
- ParallelGC 全程 STW 高吞吐；CMS 低停顿已废；G1 服务端默认
- 频繁 Full GC：jstat 看 O 列 → 不降=泄漏（jmap+MAT），降=堆小
- 泄漏是原因，溢出是结果

## 一、JVM 调优主线（最高优先级）

### 1.0 方法论骨架（先背这个，散点全挂上来）

```
第 1 步 定目标：吞吐量优先 or 延迟优先？（决定选收集器的大方向）
           ├── 吞吐量优先 → ParallelGC（批处理、后台任务）
           ├── 延迟优先、堆 < 8G → G1（MaxGCPauseMillis 控停顿）← 你的生产选择
           └── 延迟优先、超大堆 → ZGC（JDK15+）
第 2 步 监控：jstat / GC 日志 / Arthas → 拿到 GC 频率、停顿、各区使用率
第 3 步 定位：按"GC 决策树"（见 1.3）判断是参数问题还是代码问题
第 4 步 动手：优先调参数（见效快），代码问题走 Heap dump 分析
第 5 步 验证：对比调优前后 GC 日志——只改一个参数，观察，再迭代
```

> 你的画布里这三张孤图：「分析 GC 日志发现频繁 Full GC→关注老年代」「Heap dump 找泄漏源头（未关闭资源、长生命周期大对象）」「之后进行代码优化」——就是第 3、4 步的碎片，现在挂到骨架上了。

### 1.1 监控工具链（画布 JVM 区空白，必须补）

| 工具      | 作用                           | 常用命令                                                     |
| --------- | ------------------------------ | ------------------------------------------------------------ |
| jps       | 找 Java 进程 PID               | `jps -l`                                                     |
| **jstat** | **GC 统计（调优第一工具）**    | `jstat -gcutil <pid> 1000`（每秒刷新）                       |
| jmap      | 堆快照 / 对象统计              | `jmap -dump:format=b,file=heap.hprof <pid>`<br>`jmap -histo <pid> \| head -20`（看堆里什么对象最多） |
| jstack    | 线程快照（排查死锁、CPU 飙高） | `jstack <pid> > thread.dump`                                 |
| jcmd      | 综合诊断（JDK8 起推荐）        | `jcmd <pid> GC.heap_info`                                    |
| Arthas    | 线上诊断（阿里开源，生产神器） | `dashboard`（总面板）、`thread -n 3`（CPU 最高 3 线程）、`heapdump` |

**jstat -gcutil 输出列（这是真实存在的列，别多背）：**

```
S0    S1    E     O     M     YGC   YGCT    FGC   FGCT    GCT
0.00  50.0  95.0  85.0  92.0  500   2.500   50    15.000  17.500
```

- `S0/S1`：两个 Survivor 使用率（一个 0 一个有值，交替使用）
- `E`：Eden 使用率；`O`：**老年代使用率（排查频繁 Full GC 看这列）**
- `M`：元空间使用率
- `YGC/YGCT`：Young GC 次数 / 总耗时；`FGC/FGCT`：Full GC 次数 / 总耗时
- 诊断口径：**FGC 持续增长 + O 列下不来 → 老年代问题（内存泄漏或晋升过快）**；YGC 频繁但 FGC 少 → Eden 偏小

### 1.2 GC 日志：打印参数 + 怎么读（画布记了打印、没记解读）

**JDK8 打印（你画布记的 4 个参数，补全用法）：**

```bash
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log
```

**JDK9+ 统一为（JDK8 不支持 -Xlog 语法，注意别混用）：**

```bash
-Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=100m
```

**一条 JDK8 Full GC 日志逐段解读（面试能讲出来就是加分）：**

```
2026-11-16T10:15:30.123+0800: [Full GC (Metadata GC Threshold)
  [Tenured: 6142M->2048M->8192M, 3.5002300 secs]
  [Metaspace: 512M->480M(512M)], 3.5003 secs]
```

| 日志段                         | 含义                                                         | 调优看点                                      |
| ------------------------------ | ------------------------------------------------------------ | --------------------------------------------- |
| `Full GC (原因)`               | 触发原因：老年代空间不足 / Metadata GC Threshold / System.gc() | **原因直接指向调哪个区**                      |
| `Tenured: 6142M->2048M->8192M` | 老年代 回收前→回收后→总容量                                  | 回收后仍接近总容量 → 泄漏或堆太小             |
| `Metaspace: 512M->480M(512M)`  | 元空间回收前后（括号是高水位）                               | 顶到上限 → 类加载泄漏或 MaxMetaspaceSize 太小 |
| `3.5 secs`                     | 本次停顿时长                                                 | 长停顿频繁出现 → 换 G1 / 调 MaxGCPauseMillis  |

### 1.3 问题定位决策树（把你的散点串起来）

```
监控发现异常
├── 频繁 Minor GC、Full GC 少 → Eden 太小（对象朝生夕死却装不下）
│   └── 调 -Xmn 或让 SurvivorRatio 合理（你记过：Eden:S0:S1 = 8:1:1）
├── 频繁 Full GC，O 列居高不下
│   ├── 回收后 O 明显下降 → 只是堆太小/晋升过快 → 调 -Xmx、MaxTenuringThreshold
│   └── 回收后 O 几乎不降 → 【内存泄漏】← 你记过的调优链路从这里开始
│       └── jmap 导堆快照 → MAT 看 Dominator Tree / Leak Suspects
│           → 定位「未关闭的资源、长生命周期大对象」（你的原话）
│           → 代码优化（加过期策略 / try-with-resources / 用完 remove）
├── 单次停顿太长 → STW 不可控（你记过："传统GC整块回收，堆越大STW越长"）
│   └── 换 G1：Region 化 + MaxGCPauseMillis 动态选择回收量（你记过原理）
└── Metaspace 顶满 → 动态类生成（CGLIB/反射代理）→ 加大上限 / 排查类泄漏
```

### 1.4 OOM 类型大全（画布只记了堆 OOM 一句）

| OOM 信息                             | 原因                                     | 处理                                               |
| ------------------------------------ | ---------------------------------------- | -------------------------------------------------- |
| `Java heap space`                    | 堆放不下（你记的：大量对象长时间无回收） | 加 -Xmx / MAT 查泄漏                               |
| `Metaspace`                          | 类元数据超上限                           | 加 -XX:MaxMetaspaceSize / 查 CGLIB 类泄漏          |
| `GC overhead limit exceeded`         | 98% 时间在 GC 却回收不到 2%              | 堆接近耗尽，等价于堆 OOM 的前兆                    |
| `unable to create new native thread` | 线程数到系统上限                         | **减小** -Xss（每线程栈更小）、降线程数、调 ulimit |
| `Direct buffer memory`               | 直接内存耗尽                             | -XX:MaxDirectMemorySize / 查 NIO 缓冲泄漏          |

**内存泄漏 vs 内存溢出一句话**：泄漏是"原因"（对象该死没死，引用链还挂着），溢出是"结果"（空间不够）。面试必问这组概念区分。

### 1.5 容器化 JVM（你生产在 Docker，这是独家实战区）

你画布已记对的：`-Xmx4096m 不是容器总内存，容器 limit 要 5~6G，留给元空间、线程栈、native`。在此基础上补：

- **JDK8u191+ 容器感知**：`-XX:+UseContainerSupport`（默认开），JVM 能看到容器 limit 而不是宿主机内存，避免"容器 2G、JVM 按宿主机 64G 算默认堆"被 OOMKilled
- **按比例给堆**：`-XX:MaxRAMPercentage=75.0`（容器 limit 的 75% 给堆），比写死 -Xmx 更适合弹性规格
- **HeapDumpPath 坑（你画布记过 ⚠，面试可讲）**：容器重启 dump 文件就没了，必须挂载卷到 dump 路径，否则 OOM 后抓不到现场
- `ega=file:/dev/./urandom`（你记过：修容器熵不足启动慢）和 `-Dfile.encoding=UTF-8`（信创麒麟乱码坑）——你笔记里这类实战细节面试时非常加分

### 1.6 你的生产参数模板（12 条升级为"讲得出为什么"版）

你 Docker 里那套参数，面试每条都可能被追问，按你的笔记 + 补充整理：

## 三、垃圾对象判断补全（画布最薄区）

### 引用计数法为什么被抛弃

给每个对象配引用计数器，+1/-1，归零回收。**致命缺陷：循环引用**（A↔B 互相引用，都不为 0，实际都已不可达）。JVM 主流实现不用它，改用可达性分析。

### 四种引用（高频，且连接你多线程区的 ThreadLocal）

| 引用 | 类               | 回收时机                  | 典型应用                                                  |
| ---- | ---------------- | ------------------------- | --------------------------------------------------------- |
| 强   | 普通 new         | 永不主动回收（宁可 OOM）  | 普通对象                                                  |
| 软   | SoftReference    | **内存不足时**才回收      | 缓存（页面缓存、图片缓存）                                |
| 弱   | WeakReference    | **下次 GC 必回收**        | ThreadLocalMap 的 Entry key（你多线程画布记过这个泄漏链） |
| 虚   | PhantomReference | 随时可回收，get 永远 null | 堆外内存回收通知（配合引用队列）                          |

**记忆钩子**：强 → 软（内存不足才放）→ 弱（GC 就放）→ 虚（形同虚设），强度递减。

### finalize() 对象自救（可达性分析的两次标记）

不可达对象若重写了 finalize() 且未执行过，有**一次**自救机会（finalize 里重新挂回引用链）。finalize 只执行一次，且已被 JDK9 废弃（清理失败风险），面试点出"一次机会 + 已废弃"即可。

### 主动引用（触发初始化的 6 种，补你那句"首次主动使用"）

1. new / 读写静态字段（非 final 常量）
2. 反射调用（Class.forName）

### 打破双亲委派（中高级必问）

| 场景        | 为什么打破                                                   |
| ----------- | ------------------------------------------------------------ |
| SPI/JDBC    | 接口在核心库（Bootstrap 加载），实现类在 classpath——父加载器要"反向委托"子加载器（线程上下文类加载器） |

## 五、运行时数据区补全

### TLAB（Thread Local Allocation Buffer）

对象分配比你想的更卷：Eden 上再给**每个线程划一块私有分配区**，线程内分配只动指针（指针碰撞），无锁无 CAS 争用。`-XX:+UseTLAB` 默认开。
**为什么有它**：堆是共享的，多线程同时分配对象会竞争 Eden 指针；TLAB 把争用消掉。

### 对象内存布局（连多线程区的锁升级，组合高频题）

```
对象 = 对象头 + 实例数据 + 对齐填充
对象头 = Mark Word（哈希码/GC年龄/锁标志/线程ID，随锁状态变化）
       + 类型指针（指向类元数据，开启压缩指针 4 字节）
       + 数组长度（仅数组对象）
对齐填充：对象起始地址必须 8 字节整数倍，不足补齐
```

锁升级时 Mark Word 内容变化：无锁（hashcode+年龄）→ 偏向锁（线程ID+epoch）→ 轻量级（指向栈中 Lock Record 的指针）→ 重量级（指向堆中 Monitor 的指针）。**注意：偏向锁在 JDK15 起默认禁用**。

### 栈溢出 SOFE vs 堆 OOM（你只记了 OOM）

|      | StackOverflowError       | OutOfMemoryError   |
| ---- | ------------------------ | ------------------ |
| 区域 | 虚拟机栈                 | 堆/元空间等        |
| 原因 | 栈深度超限（递归没出口） | 空间装不下         |
| 参数 | -Xss（默认 1M）          | -Xmx 等            |
| 典型 | 无出口递归               | 大集合、缓存无上限 |

> 递归深度估算：-Xss 越大，每帧越小 → 能递归越深。1M 栈约万级帧。

## 六、GC 算法补全

### Minor / Major / Full GC：触发条件（你画布只记了范围，这里补"何时触发"）

| 类型     | 范围（你记过）                | 触发条件（补充）                                             |
| -------- | ----------------------------- | ------------------------------------------------------------ |
| Minor GC | 新生代（你图里的蓝箭头）      | **Eden 满**（频繁但极快，可不计较）                          |
| Major GC | 老年代                        | 老年代空间不足（常伴随至少一次 Minor）                       |
| Full GC  | 整堆+方法区（你图里的红箭头） | ①老年代不足 ②元空间不足 ③System.gc()（可用 -XX:+DisableExplicitGC 关）④**空间分配担保失败** ⑤CMS 并发失败 |

**空间分配担保（面试深挖点）**：Minor GC 前检查"老年代剩余 ≥ 新生代全部对象？"不满足则查历次晋升平均大小做担保判断，仍不放心 → 直接 Full GC，先腾老年代。

### 新生代为什么复制算法（把你对比表里的隐含逻辑显式化）

新生代对象 98% 朝生夕死 → 存活少 → 复制成本极低（只搬活的）；且用 8:1:1 而非对半分，空间浪费仅 10%。老年代存活率高 → 复制成本大 → 标记清除/整理。

### ZGC / Shenandoah（演进表后续，加分题）

- ZGC：JDK11 实验、**JDK15 生产可用**，停顿 <1ms（不是 10ms），核心技术：**染色指针 + 读屏障**，停顿不随堆大小增长（TB 级堆也可）
- Shenandoah：RedHat 出品，并发整理，低停顿
- 与 G1 的选择口径：堆 ≤ 8G 用 G1，超大堆/极致低延迟用 ZGC
